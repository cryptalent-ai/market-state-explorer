# Market State Explorer v1.3 — Decision-Oriented Visual Redesign Specification

## 0. Purpose

This is the implementation specification for the next Market State Explorer release.

The current v1.2.1 release is functionally healthy: the hosted app works, the local near-real-time relay works, the Streamlit app can fall back to delayed official Binance archives, and the underlying quantitative model is considered frozen. The remaining problem is information design: the current Effort–Result scatter/state-map and 2D trajectory remain visually dense and are difficult to interpret quickly.

v1.3 must solve that reading problem. This is primarily an information architecture and visualization redesign, not a model redesign.

The product goal is:

> Within 3–5 seconds, a user should be able to understand where the current market state is, how the recent state sequence is evolving, whether the current state is common or unusual, and whether historical validation for that state is strong enough to deserve attention.

Do not optimize for visual novelty. Optimize for fast decision-oriented reading.

---

## 1. Non-negotiable constraints

### 1.1 Quantitative model must remain unchanged

Do not change any of the following unless explicitly required to fix a bug that is independently proven by an existing failing test:

- Effort mathematics
- Result mathematics
- Positioning mathematics
- rolling normalization behavior
- thresholds
- boundary logic
- Delta reconstruction
- Open Interest alignment
- Research Event definitions
- forward-return / ATR / MFE / MAE calculations
- validation sampling logic
- no-lookahead guarantees
- relay freshness rules
- archive fallback behavior

The current codebase deliberately keeps visual concerns separate from the audited model. Preserve that separation.

### 1.2 Data-source behavior must remain intact

Preserve all current source modes:

- `Auto (Relay → Archive)`
- `Near-Real-Time Relay`
- `Binance Recent / Archive`
- `Upload CSV`

Preserve current behavior that:

- relay data is treated as current only while fresh
- stale relay data is rejected as current
- Streamlit Cloud HTTP 451 falls back to official Binance archive data
- delayed archive data is clearly labelled delayed
- future OI matches remain prohibited

### 1.3 Existing v1.2.1 must remain recoverable

Before implementation, create a branch from current `main`:

`v1.3-decision-ui`

Do not develop directly on `main`.

The current `main` should remain deployable until v1.3 is verified.

---

## 2. Current problem to solve

The current default State Map and 2D Trajectory show too many visual relationships simultaneously.

The State Map currently mixes:

- historical density
- recent states
- current state
- quadrant labels
- direction / positioning coloring

The 2D Trajectory currently mixes:

- temporal sequence
- geometric movement
- quadrant classification
- start / previous / current markers
- large jumps and local moves

The result is still difficult to interpret despite the v1.2 density and short-path improvements.

v1.3 should stop using the 2D scatter/trajectory as the primary reading surface.

They may remain available as advanced drill-down views, but they must not be the default decision interface.

---

## 3. New information architecture

### 3.1 Main navigation

Keep the existing sidebar sections, but change the visual priority:

- Dashboard
- State Map
- Trajectory
- Validation
- Data Quality
- Methodology

The section names may remain for backward familiarity, but their default contents must change as specified below.

### 3.2 Dashboard becomes the primary decision surface

The Dashboard should answer, in order:

1. What is the current state?
2. Is the current state fresh?
3. What regime has dominated recently?
4. Is the market stable, transitioning, or oscillating between states?
5. How unusual is the current state relative to the selected historical window?
6. What does historical validation say about the current state, if enough sample exists?

The Dashboard should not require the user to open a scatter plot to answer these questions.

---

## 4. Dashboard layout

### 4.1 Row A — Current State Summary

Retain the existing headline state metrics, but improve readability.

Required fields:

- Effort
- Result
- Region
- Positioning
- Strength
- Velocity
- Research

Requirements:

- Region and Positioning must display full text. No ellipsis truncation.
- Use responsive two-line text if necessary.
- Current state timestamp must be visible directly above or below the cards.
- Current source/freshness status must remain explicit.
- Relay active state should remain green.
- Delayed archive fallback should remain clearly yellow/warning.

### 4.2 Row B — State Matrix (primary replacement for default scatter)

Add a decision-oriented categorical state matrix.

#### Default matrix

Use a 2×2 Effort–Result matrix based on the existing sign-based region definitions:

- Low Effort / High Result
- High Effort / High Result
- Low Effort / Low Result
- High Effort / Low Result

Each cell must display:

- region name
- historical occupancy % in the selected history window
- recent occupancy count and % for the recent-lookback window
- current marker if the current state belongs to that region

Suggested display example:

`High Effort / Low Result`

`History: 27.4%`

`Recent 12: 7 / 12 (58.3%)`

`CURRENT`

The current cell must be visibly highlighted, but avoid alarm-style coloring unless semantically warranted.

#### Interaction

Provide controls:

- Historical window: 250 / 500 / 1000 / All available
- Recent window: 5 / 8 / 12 / 20 / 30

The matrix must update from the active dataset.

#### Optional extended matrix

If useful and straightforward, add an optional advanced 3×3 matrix using existing `BoundaryThreshold` around zero:

Effort columns:

- Low
- Near Zero
- High

Result rows:

- High
- Near Zero
- Low

This advanced mode must be optional. The default remains 2×2 for clarity.

Do not invent new model states or thresholds. If 3×3 is implemented, derive Near Zero strictly from the already-defined boundary threshold semantics.

### 4.3 Row C — Recent State Timeline Ribbon

Add a chronological ribbon view that replaces 2D trajectory as the default recent-state visualization.

The ribbon must run left-to-right in time.

Default lookback: 12 valid states.

User-selectable lookback:

- 5
- 8
- 12
- 20
- 30

Required rows:

1. Effort–Result Region
2. Positioning State
3. Research Event

Optional fourth row:

4. Boundary confidence / near-state-boundary indicator

Each time step should be a discrete cell.

Requirements:

- Most recent state must be visually obvious at the right edge.
- Hover must show full timestamp and full state details.
- Avoid using more than a small, consistent palette.
- Region and Positioning color legends must be visible but compact.
- The timeline must remain readable on normal laptop width.

The design should make persistence and transitions easy to see.

Example questions it should answer instantly:

- Has the market stayed in High Effort / Low Result for the last 6 bars?
- Did Positioning flip from Short Covering to Mixed / Low Conviction?
- Are Research Events isolated or persistent?

### 4.4 Row D — Recent State Summary

Add a compact, descriptive summary card generated strictly from calculated state data.

Required content:

- dominant region over the last N valid states
- dominant positioning state over the last N valid states
- number of region transitions over the last N states
- number of positioning transitions over the last N states
- net Effort change over the window
- net Result change over the window
- latest one-step Effort change
- latest one-step Result change
- whether current state is near a zero boundary

Use descriptive language, not trading recommendations.

Example:

`Recent 12-state regime: High Effort / Low Result dominated 7/12 states. Region changed 3 times. Positioning remained Mixed / Low Conviction for 9/12 states. Net change: Effort +0.18, Result -0.42. Current region confidence is normal.`

Do not use words such as BUY, SELL, LONG, SHORT recommendation, edge confirmed, signal, or prediction.

### 4.5 Row E — Recent State Table

Add a compact table for the most recent 5 valid states.

Required columns:

- Timestamp
- Effort
- Result
- Region
- Positioning
- Strength
- Velocity
- Research Event

Default sort: newest first.

Full text must be visible or accessible through hover. Avoid horizontal overflow where practical.

### 4.6 Row F — Current-State Validation Snapshot

Add a small validation panel for the current state.

Priority lookup order:

1. Region × Positioning State
2. Positioning State
3. Effort–Result Region

Only show a result as usable when the existing validation/sample-quality rules consider the row usable or exploratory according to current semantics.

The panel should show, per available horizon:

- Horizon
- Non-Overlapping N
- Mean Forward ATR
- Median Forward ATR
- Difference vs Baseline ATR
- 95% CI for difference vs baseline, if available
- Positive Rate
- Sample Quality
- Tail Warning

The panel must prominently distinguish:

- usable research sample
- exploratory sample
- insufficient sample

Do not imply causation or trading edge.

If no sufficiently relevant validation row exists, show:

`No sufficiently matched historical validation sample is available for the current state.`

## 5. State Map page redesign

The State Map page should no longer open with a scatter plot.

### Default content

1. Current state summary
2. State Matrix
3. Occupancy comparison
4. Current-state percentile / rarity metrics
5. Advanced visualization expander

### 5.1 Occupancy comparison

For each of the four regions, show:

- historical occupancy %
- recent occupancy %
- recent minus historical difference in percentage points

Prefer a simple horizontal bar or table over a complex plot.

### 5.2 Current-state rarity

Compute descriptive, non-predictive rarity metrics from the active historical window.

Suggested metrics:

- Effort percentile rank
- Result percentile rank
- State Strength percentile rank
- Current region historical frequency

If percentile calculation is added, use the active visible historical sample only and document this clearly.

Do not change the underlying model.

### 5.3 Advanced views

Move the existing v1.2 visuals into an expander labelled something like:

`Advanced: 2D state-space views`

Inside, retain:

- Density + recent
- Recent only
- Full scatter

The current `src/charts_v12.py` can be reused/refactored for these advanced views.

Do not delete the old scatter capability unless technically necessary.

---

## 6. Trajectory page redesign

Trajectory becomes a time-oriented page.

### Default content

1. Recent State Timeline Ribbon
2. Recent State Summary
3. Small Multiples time series

### 6.1 Small Multiples

Display four separate compact charts, vertically stacked or in a 2×2 layout depending on responsive width:

- Effort over time
- Result over time
- Strength over time
- Velocity over time

Requirements:

- common x-axis timestamps
- current point highlighted
- zero line on Effort and Result
- no unnecessary legends where a chart title is sufficient
- default lookback matches timeline lookback

### 6.2 Region transition table

Add a compact transition table listing only points where the Effort–Result Region changes.

Columns:

- Timestamp
- From Region
- To Region
- Effort
- Result

Optional second table for Positioning transitions.

### 6.3 Advanced 2D trajectory

Move the current 2D trajectory into an expander:

`Advanced: 2D phase trajectory`

It must no longer be the default view.

## 7. Visual design principles

### 7.1 Prioritize categorical reading

Users should first understand:

- current category
- persistence
- transition
- rarity

Then optionally inspect continuous geometry.

### 7.2 Avoid spaghetti paths

No default view should draw a long polyline across many 2D states.

### 7.3 Avoid excessive color semantics

Use a small, consistent palette.

Recommended behavior:

- Region colors: 4 stable colors or 4 intensity variants
- Positioning colors: reuse the existing stable mapping
- Current state: one distinctive highlight color
- Boundary uncertainty: neutral warning treatment

Do not assign red/green in ways that imply trade direction unless the semantic object truly is up/down bar direction.

### 7.4 Full labels

Region and Positioning labels must not truncate in primary decision surfaces.

### 7.5 Dark theme compatibility

Retain the existing dark theme and ensure sufficient contrast.

## 8. Data and computation requirements

Implement visualization helpers that operate only on already-derived data.

Suggested new pure functions:

- `compute_region_occupancy(frame, history, recent_n)`
- `compute_recent_state_summary(frame, recent_n)`
- `compute_state_rarity(frame, history)`
- `build_timeline_frame(frame, recent_n)`
- `extract_region_transitions(frame, recent_n)`
- `extract_positioning_transitions(frame, recent_n)`
- `match_current_validation_rows(current_row, validation_frame)`

These should live in a new non-UI module such as:

`src/state_views.py`

Do not bury core transformations inside Streamlit rendering functions.

All functions must:

- accept DataFrame input
- avoid mutating caller input
- coerce numeric chart-facing columns defensively
- tolerate missing optional columns where possible
- avoid future data access

## 10. Regression protection

Add tests proving v1.3 did not alter the model.

At minimum:

### 10.1 Derived-feature regression

Given the same fixed fixture, compare v1.2.1 baseline outputs versus v1.3 for:

- Effort score
- Result score
- Region
- Positioning State
- Strength
- Velocity
- Research Events

They must be identical.

### 10.2 Relay compatibility

Using a relay-shaped DataFrame with object/string numeric dtypes, verify:

- Dashboard renders
- State Matrix renders
- Timeline Ribbon renders
- State Summary renders
- Recent State Table renders
- State Map advanced density view serializes
- Trajectory advanced 2D view serializes

### 10.3 Archive compatibility

Using archive-like object dtypes, verify the same visual surfaces render without TypeError.

### 10.4 Validation compatibility

- Region × Positioning available
- only Positioning available
- only Region available
- no adequate sample
- insufficient sample
- exploratory sample
- usable sample

Existing no-lookahead tests must continue to pass unchanged.

## 11. Acceptance criteria

The implementation is complete only when all of the following are true.

### Dashboard

- [ ] Current state cards show full Region and Positioning labels.
- [ ] Source/freshness status is clearly visible.
- [ ] State Matrix is visible without scrolling excessively on a normal desktop viewport.
- [ ] Current region is obvious within 3 seconds.
- [ ] Historical and recent occupancy are both visible.
- [ ] Recent State Timeline Ribbon is chronological and current state is at the right edge.
- [ ] Region persistence and transitions are visually obvious.
- [ ] Positioning persistence and transitions are visually obvious.
- [ ] Recent State Summary is generated from data and contains no trade recommendation language.
- [ ] Recent 5-state table is present.
- [ ] Current-state validation snapshot is present or clearly reports that no adequate sample exists.

### State Map

- [ ] Default view is categorical/state-matrix based, not scatter based.
- [ ] Historical vs recent occupancy comparison is shown.
- [ ] Rarity/percentile descriptors are shown.
- [ ] Existing scatter views remain available only under Advanced.

### Trajectory

- [ ] Default view is time-oriented, not 2D phase-space.
- [ ] Timeline ribbon is present.
- [ ] Effort, Result, Strength, and Velocity time series are present.
- [ ] Region transitions can be read directly.
- [ ] 2D phase trajectory remains available only under Advanced.

### Reliability

- [ ] Relay mode works.
- [ ] Archive fallback works.
- [ ] Upload CSV works.
- [ ] No new Streamlit TypeError on hosted runtime.
- [ ] Plotly figures serialize.
- [ ] CI passes on Python 3.12.
- [ ] Existing tests continue to pass.
- [ ] New v1.3 tests pass.

## 12. UX validation protocol

Before merging to `main`, test the preview build with the following human-reading tasks.

A user looking at the Dashboard should be able to answer each question in under 5 seconds:

1. What is the current Effort–Result Region?
2. What is the current Positioning State?
3. Which region dominated the last 12 states?
4. Did the region change frequently or remain persistent?
5. Is the current region historically common or relatively rare?
6. Is the current observation near a zero boundary?
7. Is there enough historical validation sample to treat the current state as research-worthy?

If the user must inspect a scatter path to answer any of these, the redesign is not complete.

`v1.3 — Decision-Oriented Visual Edition`

## 14. Explicit non-goals for v1.3

Do not add:

- machine learning
- prediction models
- automated trading
- buy/sell signals
- exchange account integration
- API keys on the hosted app
- new Positioning state definitions
- new Research Event definitions
- new thresholds chosen from visual appearance
- 3D visualization
- more data sources unless required to preserve current reliability

The job of v1.3 is to make the existing state model readable and decision-oriented.
