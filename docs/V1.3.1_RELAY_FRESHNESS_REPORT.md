## Scope and implementation

- Current UTC day and previous UTC day REST snapshots are fetched again on each
  provider acquisition. This fixes reuse of checksum-valid partial payloads.
- Official immutable archives remain the first choice. Completed older dates
  retain their existing cache-hit behavior, including historical REST entries.
- Refresh fetches and validates before touching a healthy cached entry. Payload
  and digest are staged, flushed/fsynced, then individually atomically replaced
  using `Path.replace` (works on Windows). Ordinary replacement failures roll
  back the previous pair. Temporary files are cleaned; no timestamped snapshots
  accumulate after successful refreshes. Failed refreshes propagate, never
  return a stale payload as a successful acquisition.
- Two files cannot be renamed as one filesystem transaction. Existing checksum
  validation rejects a mismatched/torn pair after an abrupt process/machine
  crash; a later acquisition quarantines it and reacquires. This is not a claim
  of cross-file transactional atomicity or concurrent-process locking.
- The existing `age_seconds` retains its publication-age meaning. Added metadata:
  `market_data_age_seconds`, `publication_fresh`, `market_data_fresh`.
- Overall `fresh` requires BOTH publication and completed-through ages <= 900s.
  Missing, invalid, or future completed-through values are rejected. The source
  remains the completed 5m bar close boundary, not the latest bar open timestamp.
- Publisher checks completed-through after acquisition and again immediately
  before the comment write, after model/encoding work. Stale data exits nonzero
  with `Relay publish failed: market data is stale; completed through ..., age
  ... minutes`. The last good comment is not overwritten. Invalid/future
  boundaries and reported future OI matches are also rejected before writing.
- `--dry-run` performs acquisition, derivation, encoding, decoding, and guards
  without contacting the GitHub write endpoint. `--cache-root` permits an
  isolated persistent cache; no arguments retain the original scheduled-task
  cache and publication behavior, except the requested safety fixes.

## Preview / human acceptance procedure

Use a separate checkout of this branch, not production main. With Python 3.12:

```powershell
python -m pip install -e '.[dev]'
python -m pytest
python -m streamlit run app.py --server.headless=true
python -m scripts.publish_live_relay --dry-run --cache-root 'C:\market-state-preview\cache'
# Repeat the same command at least five minutes later, with the same cache.
```

Expected: completed-through advances to the latest completed boundary while
publication and market ages both remain <=15min when REST is available. Compare
the emitted audit JSON, not only the updated publication clock. A deliberately
stale source must exit 1 and never invoke the comment-update operation.

A Streamlit Community Cloud preview can target this branch, entrypoint `app.py`,
Python 3.12, separately from the production app. No UI redesign is included.
The existing production publisher is NOT automatically switched by this PR.
After human approval and merge, deploy both the Streamlit consumer AND Windows
publisher checkout to the approved commit; retain the original five-minute task
schedule and cache location. No cache purge is needed. Do not run a non-dry-run
publisher against the public production comment during preview acceptance.

Production merge/deployment and post-deployment online acceptance remain pending
human approval. Local official-source evidence passes; production is not claimed
fixed until both deployments have been approved and verified.
